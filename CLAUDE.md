# CLAUDE.md

Правила работы над проектом. Описание продукта и запуск - в [README.md](README.md).

## О проекте

Мини-CRM строительной компании: объекты (стройки) и задачи по ним. Две роли - постановщик (`manager`) и исполнитель (`executor`). У задачи цикл статусов `new → in_progress → review → accepted | rework → in_progress` с историей смен.

Это не просто фронтенд: **бэкенд - Supabase (Postgres + Auth + RLS)**, отдельного сервера нет. Фронт ходит в БД напрямую через `supabase-js` и считается недоверенным.

## Стек

React 19, TypeScript, Vite, SCSS, Supabase, TanStack Query, React Router, Zustand (только UI-состояние: тема), Vitest. Менеджер пакетов - pnpm, Node ≥ 20 (`nvm use`).

## Структура

```
supabase/
├─ migrations/   схема, триггеры, RLS, RPC - единственный источник правды о доступе
├─ tests/        pgTAP-тесты безопасности БД
├─ seed.sql      демо-данные (объекты, задачи в разных статусах)
└─ config.toml
src/               фронтенд по Feature-Sliced Design
```

### Фронтенд (FSD)

Слои сверху вниз: `app` → `pages` → `widgets` → `features` → `entities` → `shared`. Слой импортирует только нижележащие; слайсы одного слоя не импортируют друг друга. Публичный API слайса - `index.ts`, импорт через алиас `@/`. Сегменты: `ui/`, `model/` (логика, типы, хуки, тесты), `api/` (запросы к Supabase и ключи TanStack Query), `config/` (константы).

- `app/` - вход, провайдеры (QueryClient, Router), маршруты и guards, глобальные стили и токены.
- `pages/` - экраны: вход, объекты, карточка объекта, карточка задачи, «Мои задачи».
- `widgets/` - блоки интерфейса (шапка, список задач, история).
- `features/` - сценарии: вход/выход, форма объекта, форма задачи, смена статуса, переключение темы.
- `entities/` - `object`, `task`, `profile`, `session`: типы, правила, запросы.
- `shared/` - без знания о домене: `ui/`, `lib/`, `api/` (клиент Supabase и `database.types.ts`), `assets/icons/` (SVG через SVGR).
- Каждый компонент - отдельная папка: `Name/Name.tsx`, `Name/Name.scss`, `Name/index.ts`.

## Безопасность (главное правило)

- Все правила доступа живут в БД: RLS, права на колонки, триггеры, RPC. Интерфейс только скрывает недоступные действия, защитой он не является.
- Статус задачи меняется **только** через RPC `change_task_status`. Прямой `update` статуса и любые записи в историю закрыты правами. Таблица допустимых переходов - `private.task_transitions`; фронт зеркалит её только для показа кнопок.
- Функции `security definer` - в схеме `private`, с `set search_path = ''`, полностью квалифицированными именами и явными `grant/revoke execute`. В `public` - только RPC, которое само проверяет вызывающего.
- В политиках используем `(select auth.uid())` и `(select private.is_manager())`, политики пишем `to authenticated`, у update-политик есть и `using`, и `with check`.
- Любое изменение схемы или прав - только новой миграцией в `supabase/migrations/` (не править применённые). Новая таблица: включить RLS, явно выдать права, добавить индексы на колонки из политик, покрыть тестом.
- Секреты: `service_role` и secret-ключи не используются во фронтенде и не попадают в репозиторий. Во фронте только `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` из `.env.local` (в `.gitignore`); образец - `.env.example`. Пароль БД и токены нигде не сохраняем.
- Открытая регистрация отключена (`enable_signup = false`); пользователей создают вручную в Supabase.

## Работа с данными на фронте

- Клиент типизирован: `createClient<Database>()`; типы генерирует `pnpm db:types` после каждой миграции, руками `database.types.ts` не правим.
- Запросы - в `entities/*/api` и `features/*/api`; компоненты Supabase напрямую не вызывают. Чтение и запись - через хуки TanStack Query, ключи - фабрики (`taskKeys.detail(id)`), после мутаций инвалидируем точечно.
- RLS на `update`/`delete` не бросает ошибку, а затрагивает 0 строк: мутации идут с `.select()`, пустой ответ показываем как «нет доступа».
- Ошибки RPC приходят кодом в `message` (`transition_not_allowed`, `comment_required`, `forbidden`, `task_not_found`, `auth_required`); переводим в понятный текст в одном месте, не показываем сырые.
- UI показывает только действия, доступные текущему пользователю в текущем статусе (`getAvailableActions` - чистая функция с тестами).

## Код

- Функции и компоненты объявлять через `const` (стрелочные), без `function`.
- Без комментариев, если они не необходимы; в SQL - короткий комментарий «зачем» над объектом, если не очевидно.
- Никакого `any`; `unknown` + сужение типов для внешних данных. Без небезопасных `as` и `!` - type guards.
- Только функциональные компоненты и хуки; производные значения вычислять, а не хранить; зависимости эффектов указывать корректно.
- Небольшие компоненты с одной ответственностью, логика отдельно от представления. UI-компоненты из `shared` не импортируют доменный код.
- Минимум зависимостей: не добавлять пакеты и не менять архитектуру без необходимости.

## UI

- Дизайн и темы - как в эталоне `task-list-plus`: светлая/тёмная тема через `data-theme` и CSS-переменные из `app/styles/global.scss`, цвета только через токены, никаких «голых» hex в компонентах.
- Стили - SCSS рядом с компонентом, БЭМ-именование.
- Семантический HTML, доступность с клавиатуры, `aria-*` где нужно; состояния hover / focus-visible / active / disabled; адаптивность ≤ 480px; анимации уважают `prefers-reduced-motion`.
- У каждого экрана есть состояния загрузки, пустого списка и ошибки.

## Тесты

- Фронт (Vitest): бизнес-логика и критические сценарии (доступные действия по роли и статусу, форматирование, маппинг ошибок), а не детали вёрстки. Названия тестов - на русском.
- БД (pgTAP, `pnpm db:test`, нужен Docker): тесты под ролями `manager` и `executor` через `set local role authenticated` и `request.jwt.claims`. Обязательно покрыты: чужая задача не читается, прямой `update status` и запись в историю падают, запрещённые переходы и «доработка» без комментария падают, исполнитель не создаёт и не удаляет. Каждый тест в `begin ... rollback`. RLS на select/update/delete молчит, поэтому проверяем пустой результат и неизменённое состояние.

## Перед завершением изменений

Обязательно запустить и добиться успеха: `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`; при изменениях в `supabase/` - ещё `pnpm db:test`.

## Git

- Коммиты делает только пользователь. Ассистент не выполняет `git commit`, `git push`, `git reset`, `git rebase`, `git init` и не правит историю.
- После каждого этапа плана ассистент останавливается, перечисляет изменения и даёт текст коммита (Conventional Commits: `feat`, `fix`, `chore`, `docs`, `test`, `refactor`); следующий этап - только после команды пользователя.
- Перед коммитом проверки выше должны быть зелёными (husky запускает lint-staged, перед push - typecheck и тесты).
- Внешние сервисы (деплой, `db push` в облако) - только с разрешения пользователя.
